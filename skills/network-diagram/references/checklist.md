# 구성도 점검 체크리스트

명세를 다 쓴 뒤, 그리기 전에 아래를 하나씩 확인한다. 문제를 찾으면 고치거나 `mark: assume` 과 `notes` 로 드러낸다. 사용자가 모르는 값을 지어내서 확정된 것처럼 쓰지 않는다.

## 1. 경계
- [ ] 인터넷과 내부망 사이에 방화벽(또는 공유기·UTM)이 있다.
- [ ] 외부에 공개하는 서버(웹, API, 외부 연계 수신)가 있으면 **DMZ** 를 따로 두고, DMZ 는 **방화벽의 별도 인터페이스**에 연결한다. 내부 코어 스위치에 DMZ 스위치를 바로 붙이지 않는다.
- [ ] 외부 연계 시스템, 원격 사용자 등 바깥에서 오는 연결은 반드시 `internet` 을 거쳐 방화벽으로 들어온다. 방화벽을 건너뛰는 선을 그리지 않는다.

## 2. 거점 연결
- [ ] 거점이 둘 이상이면 연결 방식(VPN, 전용선)을 정한다. 모르면 VPN 으로 두고 `assume`.
- [ ] VPN 장비는 방화벽 안쪽이나 방화벽 내장(UTM)으로 둔다. 방화벽 바깥에 노출된 VPN 장비로 그리지 않는다.
- [ ] 거점마다 사설 대역이 **겹치지 않는다** (겹치면 VPN 라우팅 불가).

## 3. 장비 연결
- [ ] 무선 단말은 AP 를 거친다 (`[ap, sensor, wifi]`). 무선 단말을 서버에 바로 잇지 않는다.
- [ ] 카메라·AP 가 여러 대면 PoE 스위치를 둔다 (모르면 `mark: add`).
- [ ] 장비끼리 사슬처럼 잇지 않는다. 같은 망의 서버들은 각각 스위치에 연결한다.
- [ ] 서로 다른 VLAN/대역 사이 통신이 있으면 L3 스위치나 라우터가 있다.
- [ ] 연결선이 없는 장비가 없다 (렌더러가 경고함).

## 4. 주소와 정책
- [ ] 영역마다 `cidr` (모르면 예시 대역 + `notes` 에 "예시").
- [ ] 주요 흐름마다 `flows` 한 줄: 출발, 목적, 포트.
- [ ] DMZ → 내부는 필요한 포트만 허용, DMZ → DB 직접 접근은 `deny: true` 로 명시.
- [ ] 외부 → 내부 공개 서비스는 방화벽 NAT(포트포워딩)를 `note` 에 적는다.

## 5. 표기
- [ ] 한 그림에 한 질문. 너무 크면 거점별·주제별로 나눈다.
- [ ] 신규 도입은 `mark: new`, 가정은 `mark: assume`, 그리고 하단 `notes` 에 이유.
- [ ] 이름(`label`)은 사용자가 쓰는 말 그대로. 약어는 `sub` 에 풀어 쓴다.
